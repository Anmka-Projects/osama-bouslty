# مواصفة الباك إند — التصنيفات الفرعية (Subcategories)

التطبيق دلوقتي بيدعم تصنيفات بمستويين (تصنيف رئيسي → تصنيفات فرعية). الملف ده يوضح المطلوب من الباك.

## 1) موديل البيانات

إضافة علاقة self-referencing على جدول `categories`:

```
categories.parent_id → BIGINT UNSIGNED NULL
                       FOREIGN KEY → categories.id
                       ON DELETE SET NULL (أو RESTRICT لو عايزين تمنعوا حذف أب عليه أولاد)
```

- `parent_id = null` → تصنيف رئيسي.
- `parent_id = {id}` → تصنيف فرعي.
- مستوى واحد من التداخل كافي (أب → أولاد). التطبيق بيتعامل مع تداخل أعمق لو حصل، لكن الأفضل نظاميًا مستويين بس.

## 2) استجابة `GET /api/categories`

التطبيق بيقبل **أي شكل من الاتنين** — اختاروا اللي أسهل:

### الخيار A — متداخل (مفضّل)

```json
{
  "success": true,
  "data": [
    {
      "id": 1,
      "name": "Programming",
      "name_ar": "برمجة",
      "icon": "/storage/icons/code.png",
      "color": "#7C3AED",
      "courses_count": 24,
      "children": [
        {
          "id": 11,
          "name": "Flutter",
          "name_ar": "فلاتر",
          "parent_id": 1,
          "icon": "...",
          "color": "#02569B",
          "courses_count": 8
        },
        {
          "id": 12,
          "name": "Python",
          "name_ar": "بايثون",
          "parent_id": 1,
          "courses_count": 16
        }
      ]
    }
  ]
}
```

### الخيار B — مسطح مع `parent_id`

```json
{
  "data": [
    { "id": 1,  "name": "Programming", "parent_id": null },
    { "id": 11, "name": "Flutter",     "parent_id": 1 },
    { "id": 12, "name": "Python",      "parent_id": 1 }
  ]
}
```

> ملاحظات التوافق:
> - التطبيق بيقبل اسماء بديلة للأولاد: `children` / `subcategories` / `sub_categories` / `subCategories`.
> - وبدائل للأب: `parent_id` / `parentId` / `parent` (object فيه `id`).
> - **مهم:** في الشكل المسطح لو `parent_id` رجع `0` أو `"0"` بدل `null` التطبيق بيعتبره تصنيف رئيسي.

## 3) كورسات التصنيف — `GET /api/categories/{id}/courses`

- لما `{id}` يكون **تصنيف فرعي** → يرجع كورساته بس (سلوك طبيعي، التطبيق جاهز).
- لما `{id}` يكون **تصنيف أب** → المفروض يرجع **كورسات الأب + كل أولاده** (descendants) عشان لو حد دخل على كورسات الأب مباشرة يشوف كل حاجة.
- `courses_count` في التصنيف الأب الأفضل يكون **مجموع** كورساته + كورسات أولاده.

## 4) تفاصيل الكورس

- `course.category_id` ممكن يشاور على **تصنيف فرعي** — مفيش مشكلة.
- الأفضل (اختياري) ترجعوا `category` object جوه الكورس فيه `parent_id` عشان التطبيق يقدر يعمل breadcrumb "برمجة › فلاتر" لو احتجناه بعدين.

## 5) الأدمن — `GET /api/admin/categories` + إنشاء/تعديل

- نفس الشكل (أو المسطح) للـ admin endpoint — شاشة إنشاء الكورس للمحاضر بتستخدمه وتدعم الاتنين.
- `POST/PUT /api/admin/categories` يقبل `parent_id` اختياري:
  ```json
  { "name": "Flutter", "name_ar": "فلاتر", "parent_id": 1 }
  ```
- فاليديشن مقترح:
  - `parent_id` موجود ومش هو نفس الـ id (منع الدوران).
  - الأب نفسه ميكونش ابن (لو عايزين تحددوا العمق بمستويين).
  - حذف أب عليه أولاد → إما ممنوع (422) أو الأولاد `parent_id` تبقى `null`.

## 6) سلوك التطبيق (للعلم)

- شاشة التصنيفات بتعرض الرئيسية بس؛ الضغط على تصنيف عنده أولاد → شاشة فرعية بنفس التصميم؛ الضغط على ورقة (مفيهاش أولاد) → كورسات التصنيف.
- كارت الأب بيظهر **عدد التصنيفات الفرعية** بدل عدد الكورسات.
- دروب داون اختيار التصنيف في إنشاء الكورس بيظهر الشجرة مسطحة بمسافة بادئة (`— ابن`).

## 7) ملخص المطلوب

1. عمود `parent_id` على `categories` + إرجاعه في كل الـ endpoints.
2. ريسبونس متداخل (`children`) **أو** مسطح بـ `parent_id` — الاتنين مدعومين.
3. `categories/{id}/courses` للأب يرجع كورسات أولاده كمان.
4. `parent_id` مقبول في إنشاء/تعديل التصنيف من الأدمن.
